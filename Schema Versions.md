AVRO Schema Versions

Apache Avro — это формат сериализации данных, который поддерживает схему (schema) для структурированных данных.
Чтобы управлять изменениями схемы, используется версионирование AVRO-схем.

Типы совместимости схем (Schema Compatibility)

При обновлении схемы важно учитывать совместимость с уже записанными данными.

Тип совместимости Описание Поддерживаемые изменения
Backward Новая схема может читать старые данные. ✅ Добавление полей с default значением.
Forward Старая схема может читать новые данные. ✅ Удаление полей или добавление полей с default.
Full Поддерживает и Backward, и Forward. ✅ Только совместимые изменения.
None Совместимость не проверяется. ❌ Любые изменения возможны.

Пример изменения AVRO-схемы

📌 Исходная схема (v1):

{
"type": "record",
"name": "User",
"fields": [
{"name": "id", "type": "int"},
{"name": "name", "type": "string"}
]
}

📌 Обновлённая схема (v2, Backward-compatible):

{
"type": "record",
"name": "User",
"fields": [
{"name": "id", "type": "int"},
{"name": "name", "type": "string"},
{"name": "email", "type": ["null", "string"], "default": null}
]
}

✅ Новое поле email добавлено с default, поэтому Backward-compatible.

Где хранятся версии?
• В Schema Registry (например, Confluent Schema Registry).
• В метаданных AVRO-файлов.

Вывод
• AVRO Schema Versions позволяют безопасно обновлять схемы данных.
• Выбор типа совместимости зависит от бизнес-требований и требований к данным. 🚀

Schema Versions и их использование в форматах данных

Schema Versioning (версии схем) — это механизм управления изменениями структуры данных в форматах сериализации.
Используется для обеспечения совместимости данных при обновлении схем.

⸻

Где используется версия схемы?

Формат Описание Где хранится схема?
AVRO Бинарный формат, оптимизированный для хранения и передачи данных. В Schema Registry или в заголовке AVRO-файла.
Protobuf Формат сериализации от Google, широко используется в gRPC. В .proto файлах, в коде сервисов.
JSON Schema Определяет структуру JSON-документов для валидации и сериализации. В .json-файлах или API-документации.
Thrift Разработан Facebook, использует компактное бинарное представление. В .thrift файлах.
Parquet Колоннарный формат хранения данных, часто применяется в DWH и Big Data. В файловых метаданных Parquet.
ORC Оптимизированный для Apache Hive бинарный формат. В метаданных файлов ORC.

⸻

Типы совместимости схем

При обновлении схем важно, чтобы старые и новые версии оставались совместимыми.

Тип совместимости Описание
Backward Новая схема читает старые данные.
Forward Старая схема читает новые данные.
Full Поддерживает Backward и Forward.
None Нет проверки совместимости.

⸻

Примеры использования
• Kafka + AVRO → Использование Schema Registry для валидации схем сообщений.
• gRPC + Protobuf → Сервисное API хранит .proto файлы и контролирует изменения.
• Data Lake (Parquet/ORC) → Аналитические хранилища используют схемы в метаданных.

⸻

Вывод

Schema Versioning необходим для гибкого управления изменениями данных,
особенно в распределённых системах, API и хранилищах данных. 🚀

Что делать при изменении схемы данных в S3?

Когда схема данных изменяется, важно обеспечить совместимость новых и старых данных в S3.
Действия зависят от типа изменения схемы и формата хранения данных.

⸻

1. Определите тип изменения схемы

Тип изменения Описание Совместимость Что делать?
Добавление нового поля Добавлен новый атрибут, старые данные его не имеют. ✅ Backward 1️⃣ Ничего не делать (если данные
JSON/Parquet/AVRO). 2️⃣ Указать default для нового поля (AVRO, Protobuf).
Удаление поля Убрали поле, которое было в старых данных. ❌ Backward ⚠ Forward 1️⃣ Не удалять физически, оставить NULL.
2️⃣ Использовать новую схему в читателях.
Изменение типа данных Например, int → string. ❌ Backward ❌ Forward 1️⃣ Конвертировать старые данные в новый формат. 2️⃣
Использовать versioned readers.
Изменение структуры (nested → flat)    Данные реструктурированы. ❌ Backward ❌ Forward 1️⃣ Миграция всех данных. 2️⃣
Использовать ETL-процесс для трансформации.

⸻

2. Выберите стратегию хранения

Метод Описание Когда использовать?
Версионирование схем (Schema Evolution)    Использовать AVRO, Parquet, ORC, где схема может изменяться автоматически.
Если данные хранятся в колоннарных форматах.
Версионирование данных (New Path)    Хранить новые данные в s3://bucket/data/v2/, старые – в s3://bucket/data/v1/. Если
изменения разрушающие (например, изменение типов).
ETL-трансформация (Reprocessing)    Читаем старые данные, конвертируем в новую схему и перезаписываем. Если изменения
некритичные, но несовместимые.
Параллельное чтение (Multi-Reader)    Обработчики данных понимают обе схемы и работают в зависимости от версии. Если
нужно гибко работать с разными схемами.

⸻

3. Пример обработки в AVRO с Schema Registry

Если храним AVRO в S3, можно использовать Schema Registry для управления версиями:

1️⃣ Добавляем новую версию схемы:

{
"type": "record",
"name": "User",
"fields": [
{ "name": "id", "type": "int" },
{ "name": "name", "type": "string" },
{ "name": "email", "type": ["null", "string"], "default": null } // Добавлено поле
]
}

2️⃣ Обновляем writer: Новый код начинает писать с новой схемой.
3️⃣ Обновляем reader: Читатель поддерживает обе схемы.

⸻

Вывод
• Минорные изменения (новые поля, удаление) – можно ничего не менять, если формат поддерживает Schema Evolution.
• Критические изменения (изменение типов, структуры) – требуют миграции данных или версионирования S3.
• Лучший подход – использовать AVRO, Parquet, ORC и Schema Registry для автоматического управления схемами. 🚀
