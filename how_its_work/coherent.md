# ETL-процесс на AWS: обработка данных с использованием Lambda, S3 и Redshift

## Архитектура проекта

Проект реализовывал **ETL-пайплайн** на **AWS**, в котором данные загружались из **REST API**, обрабатывались в **AWS
Lambda** и сохранялись в **Amazon Redshift**.

### **Основной поток обработки**

1️⃣ **Извлечение данных**

- Источник: **REST API (Dairy Data Warehouse)**.
- Запросы отправлялись из **AWS Lambda**, обрабатывались в многопоточном режиме.

2️⃣ **Обработка в AWS Lambda**

- Лямбды выполняли очистку, трансформацию и валидацию данных.
- Использовали **/tmp/** для временного хранения файлов.
- Ошибки обрабатывались через **try/catch**, статус обрабатываемых данных сохранялся.

3️⃣ **Хранение промежуточных данных**

- **S3** использовался как буферное хранилище.
- Данные сохранялись в **партицированной структуре (year/month/day)**.
- Запуск следующих лямбд осуществлялся через **Step Functions**.

4️⃣ **Загрузка в Amazon Redshift**

- Использовалась команда **COPY** для быстрой вставки данных.
- Хранилище поддерживало **стадии raw и staging**.

## Надёжность и отказоустойчивость

✅ **CloudWatch** использовался для логирования и мониторинга.  
✅ В случае ошибки данные сохранялись в **S3**, а обработка продолжалась.  
✅ Для повторного запуска использовали **Step Functions**.

## Оптимизация и масштабирование

- **Многопоточная обработка** в Lambda сокращала время выполнения.
- **S3ObjectManager** выполнял асинхронную загрузку в S3.
- Использование **COPY вместо INSERT** ускоряло загрузку в Redshift.

## Безопасность

🔒 **IAM-роли** контролировали доступ к сервисам.  
🔒 **Secrets Manager** хранил креды для Redshift.

## Альтернативы и улучшения

🔹 Рассматривался вариант использования **Glue вместо Lambda** для сложных трансформаций.  
🔹 Если нужен real-time, можно было бы использовать **Kinesis + Lambda**.  
🔹 Для улучшения скорости можно было бы применять **Redshift Spectrum для S3-запросов**.

Deploy Lambda

На проекте мы выбрали AWS Lambda + S3 + Terraform для деплоя кода. Этот подход оказался простым, надёжным и экономичным.

Как это работает:

1️⃣ GitHub Actions отслеживает изменения в main, упаковывает код и загружает .zip в S3.
2️⃣ S3 Versioning хранит все версии .zip, позволяя легко откатываться назад.
3️⃣ Terraform автоматически подтягивает последнюю версию архива из S3 и раскатывает её на Lambda.
4️⃣ Lambda Layers для зависимостей деплоятся аналогично – через отдельный .zip в S3.

Почему именно так?

✅ Нет лишних затрат – Lambda запускается раз в день, значит, платим только за реальное выполнение.
✅ Минимум сложностей – не нужны папки с датами, Terraform всегда берёт актуальную версию.
✅ Простота откатов – если новый код сломался, можно быстро переключиться на предыдущий VersionId в S3.
✅ Автоматизация – вся цепочка от коммита до продакшена работает без ручных действий.

Такой подход позволил нам быстро и стабильно деплоить код, экономя время и деньги.
