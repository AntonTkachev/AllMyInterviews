# Concurrency

**Atomic** —
Позволяет выполнять атомарные операции, эти операции выполняются как единое целое и не могут быть прерваны.

***.incrementAndGet() класса AtomicInteger атомарно увеличивает значение счетчика на один и возвращает новое
значение. Таким образом, даже если два потока одновременно вызовут этот метод, счетчик корректно увеличится на два.***

**Volatile** —
Ключевое слово гарантирует, что значение переменной будет сразу же записано в основную память, а не в кэш процессора, и
любые другие потоки будут видеть это обновленное значение.

***Если объявить счетчик как volatile int, то любые изменения его значения будут сразу же записаны в основную память, и
другие потоки будут видеть это новое значение. Однако это не гарантирует атомарности операций. Eсли два потока
одновременно прочитают значение счетчика, увеличат его на один и запишут обратно, проблема с увеличением счетчика только
на один, а не на два, все еще останется.***

**Synchronized** —
Ключевое слово используется для обозначения блоков кода или методов, которые могут быть выполнены только одним потоком в
одно и то же время.

***Если применить synchronized к методу увеличения счетчика, то в любой момент времени только один поток сможет
выполнить этот метод. Если другой поток попытается выполнить этот метод в то же время, он будет ждать, пока первый поток
не завершит работу.***

# **Что такое монитор в Java?**

## **Определение**

Монитор в Java — это механизм синхронизации, который позволяет нескольким потокам безопасно обращаться к общему ресурсу,
предотвращая состояния гонки (`race condition`). Каждый объект в Java может быть монитором.

## **Как работает монитор?**

- У **каждого объекта** есть **монитор** (intrinsic lock), который может быть **захвачен только одним потоком**
  одновременно.
- **Остальные потоки** будут заблокированы (ожидать), пока монитор не освободится.
- Монитор автоматически используется при работе с `synchronized` в Java.

## **wait / notify / notifyAll и их аналоги в `java.util.concurrent`**

### **Основные механизмы:**

- **`wait()`** – приостанавливает поток до тех пор, пока он не будет разбужен `notify()` / `notifyAll()`.
    - Имеет перегруженные версии с таймаутом.
    - Поток помещается в `wait-set` объекта.
    - Перед вызовом `wait()` **обязательно** нужно захватить монитор (`synchronized`).
    - Важная особенность: **после вызова `wait()` поток освобождает монитор**, позволяя другим потокам войти в
      `synchronized`-блок.

- **`notify()`** – будит **один** из потоков из `wait-set`, но:
    - **Не освобождает монитор** сразу после вызова.
    - Поток, который вызвал `notify()`, **должен завершить критическую секцию**, прежде чем пробуждённый поток сможет
      продолжить выполнение.

- **`notifyAll()`** – пробуждает **все** потоки в `wait-set`, но:
    - Потоки начинают борьбу (`contention`) за монитор.
    - Работает аналогично `notify()`, но даёт всем ожидающим потокам шанс продолжить выполнение.

### **Дополнительные особенности:**

- Поток, ожидающий в `wait()`, может быть разбужен:
    - **Через `notify()` / `notifyAll()`** (нормальный сценарий).
    - **Через `interrupt()`** – выбросится `InterruptedException`.
    - **Из-за `spurious wake-up`** (ложное пробуждение, поэтому `wait()` всегда вызывают в `while`-цикле, а не в `if`).
    - **По таймауту**, если используется перегруженная версия `wait(time)`.

### **Современный аналог `wait/notify/notifyAll` в `java.util.concurrent`**

- **`Condition`** из `java.util.concurrent.locks.Lock` – более гибкий механизм с явным управлением ожиданием и
  пробуждением потоков.
    - `await()` – аналог `wait()`, но **не требует `synchronized`**, а работает с `Lock`.
    - `signal()` – аналог `notify()`, будит **один** ожидающий поток.
    - `signalAll()` – аналог `notifyAll()`, будит **все** ожидающие потоки.
    - Позволяет использовать **несколько условных переменных** для более гибкого управления многопоточностью.

**Проблемы:**

**Deadlock** — Ситуация, при которой два или более потоков блокируют друг друга, ожидая освобождения ресурсов, занятых
другими потоками, что приводит к бесконечному ожиданию и невозможности продолжить выполнение.

- Решение: Использование таймаутов при блокировке, избегание вложенных блокировок, использование алгоритмов обнаружения
  и предотвращения deadlock.

**Race condition** — Ошибка проектирования, при которой работа системы или приложения зависит от того, в каком порядке
выполняются части кода.

- Решение: Использование синхронизации, атомарных операций и других механизмов управления доступом к общим ресурсам.

**Livelock** — Ситуация, при которой два или более потоков постоянно меняют свое состояние в ответ на действия друг
друга, но ни один из них не может продолжить выполнение.

- Решение: Использование алгоритмов, которые гарантируют прогресс выполнения, таких как backoff-алгоритмы.

**Starvation** — Ситуация, при которой один или несколько потоков не могут получить доступ к необходимым ресурсам и,
следовательно, не могут продолжить выполнение.

- Решение: Использование справедливых блокировок и планировщиков, которые гарантируют, что все потоки получат доступ к
  ресурсам.

**Resource contention** — Ситуация, при которой несколько потоков конкурируют за один и тот же ресурс, что может
привести к снижению производительности.

- Решение: Оптимизация доступа к ресурсам, использование пулов ресурсов и уменьшение времени удержания блокировок.

**Thread pool** —
Набор предварительно инициализированных потоков.
Если задач больше, чем потоков, то задачи ждут в очереди (Task Queue). Из очереди задача попадает на исполнение к потоку
из пула,
а после выполнения задачи поток забирает новую задачу из очереди. После выполнения всех задач из очереди потоки остаются
активными и ждут новых задач.

**Зачем использовать Thread Pool?** —

- Помогает увеличить производительность программы благодаря созданию потоков один раз (создание потока считается
  достаточно тяжёлой операцией).
- Предоставляет удобный интерфейс для работы с многопоточностью.

**ConcurrentHashMap** —  
Вместо блокировки всей карты, ConcurrentHashMap разделяет ее на несколько сегментов и блокирует только те сегменты,
которые в данный момент изменяются.
Это позволяет другим потокам параллельно работать с остальными сегментами карты, что значительно улучшает
производительность при работе с большим количеством потоков.

-----
ReentrantLock

🔹 ReentrantLock — это альтернатива synchronized, которая позволяет гибко управлять блокировками.
🔹 Один поток может повторно захватить лок, не блокируя себя.
🔹 Поддерживает тайм-аут ожидания (tryLock), условия (Condition), более тонкое управление.
🔹 Требует ручного освобождения блокировки (lock.unlock()).

Когда использовать?
✔ Нужен контроль за блокировками (например, попытка захвата с таймаутом).
✔ Требуется несколько условий ожидания (Condition).
✔ synchronized недостаточно гибок.

-----
ThreadLocal

🔹 ThreadLocal<T> — это механизм хранения уникальных переменных для каждого потока.
🔹 Значения не разделяются между потоками, нет необходимости в синхронизации.
🔹 Полезен для хранения контекста запроса, транзакций, логирования в многопоточной среде.

private static ThreadLocal<Integer> threadLocalValue = ThreadLocal.withInitial(() -> 0);

Когда использовать?
✔ Нужен уникальный объект на поток (например, UserContext).
✔ Хранение данных без передачи их через параметры.
✔ Избегание проблем с общей синхронизацией.

Важно: remove() очищает память, иначе возможны утечки.
