## Data Warehouse

Это хранилище разных данных, которые уже отсортированы и преобразованы.  
Хранилище, предназначенное для сбора и аналитической обработки исторических данных организации.
В DWH данные аккумулируют и очищают, формируя единый источник.

#### DWH vs СУБД

**DWH** предназначено для анализа данных, которые поступают в него с определённой периодичностью — например, ежечасно
или ежедневно. Оно разворачивается поверх СУБД и способно быстро обрабатывать большие массивы данных  
**DWH** фактически — инструмент для комплексного анализа данных из множества источников: по определенным заданным
параметрам

**СУБД** в основном предназначены не для аналитики, а для повседневной работы. Информация в них обновляется в реальном
времени.

## Data Lake

Это репозиторий, в котором хранятся огромные объемы необработанных данных в исходном формате до тех пор, пока они не
потребуются.
Каждому элементу данных присваивается уникальный идентификатор, и он помечается набором расширенных тегов метаданных.
Когда возникает деловой вопрос, пользователь может найти и извлечь из озера нужные ему файлы.

### ETL и ELT

**Data Warehouse** использует метод **ETL – Extract, Transform и Load**, то есть дословно переводится как «извлечение»,
«преобразование» и «загрузка».  
**Data Lake** использует **ELT — Extract, Load и Transform**, то есть сначала идет «загрузка», а только потом
«преобразование».

**Схема на запись** — Data Warehouse, когда неправильная схема - будет ошибка, ETL  
**Схема на чтение** — Data Lake, можно писать что угодно, но когда читаем нужно применять схему, ELT

# Delta Lake и Apache Iceberg: Форматы таблиц для Data Lake

## Delta Lake

**Delta Lake** — это расширение формата Parquet, добавляющее ACID-транзакции, версионность данных и управление
метаданными. Используется в Databricks и позволяет работать с большими объемами данных, сочетая возможности
транзакционной обработки и аналитики.

### Как Delta Lake работает?

- **Физически данные хранятся в формате Parquet**.
- **Папка _delta_log** содержит журналы транзакций и метаданные, отслеживая все изменения в таблице.

### Преимущества Delta Lake:

- **ACID-транзакции** обеспечивают целостность данных.
- **Time Travel** позволяет откатываться к прошлым версиям.
- **Оптимизация данных** уменьшает фрагментацию и ускоряет чтение.

## Apache Iceberg

**Apache Iceberg** — это формат таблиц для Data Lake, решающий проблемы масштабируемости, эволюции схемы и эффективности
хранения метаданных. Поддерживается в **Spark, Flink, Trino, Presto, Hive**.

### Как Iceberg хранит данные?

- **Manifest Files** содержат ссылки на файлы Parquet, ORC или Avro.
- **Manifest List** группирует манифесты для быстрого поиска.
- **Metadata Files** управляют снимками данных (snapshots).

### Преимущества Iceberg:

- **ACID-транзакции** и согласованность данных.
- **Эволюция партиционирования** без переразбиения данных.
- **Масштабируемые метаданные**, эффективные при больших объемах данных.

## Сравнение Delta Lake и Iceberg

| Функция                          | Delta Lake                  | Iceberg                  |
|----------------------------------|-----------------------------|--------------------------|
| **ACID-транзакции**              | ✅ Да                        | ✅ Да                     |
| **Time Travel**                  | ✅ Да                        | ✅ Да                     |
| **Эволюция партиционирования**   | ❌ Нет                       | ✅ Да                     |
| **Удаление и обновление данных** | ⚠️ Медленно (Copy-on-Write) | ✅ Быстро (Merge-on-Read) |
| **Оптимизация метаданных**       | ❌ Ограниченная (JSON-лог)   | ✅ Масштабируемая         |

## Итог

Delta Lake и Iceberg расширяют возможности Parquet, делая его основой для надежных транзакционных таблиц. Delta
ориентирована на Databricks, Iceberg предлагает гибкость и масштабируемость. Выбор зависит от архитектуры и потребностей
работы с данными.

## OLTP vs OLAP

OLTP — транзакционные БД используемые в банках, e-commerce и CRM-системах. Они обеспечивают быструю вставку, обновление
и удаление данных, используют нормализованные схемы для минимизации дублирования, работают с небольшими объемами данных
и требуют высокой скорости отклика. PostgreSQL

OLAP — аналитические БД, для работы с большими объемами исторических данных. Они применяют денормализованные структуры,
обеспечивая быстрые агрегированные вычисления и сложные аналитические запросы, часто используются в BI-системах и
хранилищах данных вроде Amazon Redshift и Google BigQuery.

# ** RDBMS vs NoSQL**

## **Реляционные базы данных (SQL)**

Реляционная база данных (RDBMS) хранит данные в виде таблиц со строгой структурой, где каждая строка представляет
запись, а столбцы — поля с определёнными типами данных. Все данные связаны между собой через первичные и внешние ключи.

### **Преимущества SQL:**

- Соответствие требованиям **ACID** (атомарность, согласованность, изолированность, долговечность)
- **Целостность данных** благодаря строгим связям между таблицами
- **Четкая структура** упрощает анализ и обработку данных

### **Недостатки SQL:**

❌ Плохо **масштабируются горизонтально**, сложность в распределенных хранилищах  
❌ **Сложность проектирования** больших баз с множеством связей  
❌ **Эволюция схемы данных** отстает от потребностей бизнеса, требует сложных миграций

### **Примеры SQL-баз данных:**

- **Oracle** – мощная коммерческая база с поддержкой высоконагруженных систем
- **MySQL** – популярная open-source БД для веб-приложений
- **SQL Server** – реляционная БД от Microsoft
- **PostgreSQL** – мощная open-source БД с поддержкой расширенных SQL-функций

---

## **Нереляционные базы данных (NoSQL)**

NoSQL базы хранят данные в **гибких структурах** (документы, графы, ключ-значение, колонки), обеспечивая высокую
скорость обработки и горизонтальную масштабируемость.

### **Преимущества NoSQL:**

- **Высокая скорость обработки данных**
- **Горизонтальное масштабирование** – легко адаптируются к нагрузке
- **Гибкость схемы** – можно хранить разнородные данные без строгих ограничений

### **Недостатки NoSQL:**

❌ Не все NoSQL базы поддерживают **ACID**, возможны проблемы с консистентностью  
❌ Нет **универсального стандарта** для работы с данными  
❌ **Сложность в сложных аналитических запросах**, отсутствие SQL

### **Типы NoSQL баз данных:**

| **Тип NoSQL**                     | **Описание**                                                      | **Примеры**           |
|-----------------------------------|-------------------------------------------------------------------|-----------------------|
| **Ключ-значение** (Key-Value)     | Данные хранятся в формате "ключ → значение", аналогично HashMap   | Redis, DynamoDB, Riak |
| **Документные базы** (Document)   | Хранят данные в формате JSON/BSON, структура документов гибкая    | MongoDB, CouchDB      |
| **Колоночные хранилища** (Column) | Данные хранятся в столбцах для оптимизации аналитических запросов | Cassandra, HBase      |
| **Графовые базы** (Graph)         | Хранят узлы и связи между ними, используются в социальных сетях   | Neo4j, ArangoDB       |

### **Примеры NoSQL баз данных:**

- **MongoDB** – документная БД с JSON-ориентированным хранилищем
- **Cassandra** – распределенная БД с высокой доступностью
- **HBase** – масштабируемая БД, интегрированная с Hadoop

---

## **SQL vs NoSQL: Что быстрее?**

- **SQL** базы подходят для **сложных аналитических запросов**, требующих строгих связей между данными.
- **NoSQL** базы лучше при **больших нагрузках**, где важны **скорость и масштабируемость**.
- Выбор зависит от **конкретных задач** проекта.

# **Snowflake – облачное хранилище данных (Data Warehouse)**

Snowflake — DWH разработанное для аналитики больших данных и построенное по мультиоблачной архитектуре. Оно не требует
управления инфраструктурой и позволяет масштабировать вычислительные ресурсы и хранилище независимо друг от друга.

🔹 Ключевые особенности Snowflake

- Отделение хранения от вычислений – хранилище данных (Storage) и вычислительные ресурсы (Compute) масштабируются
  независимо друг от друга.
- Полностью управляемый SaaS – не требует настройки серверов и кластеров.
- Автоматическое горизонтальное масштабирование – ресурсы автоматически увеличиваются/уменьшаются в зависимости от
  нагрузки.
- Поддержка структурированных и полу-структурированных данных – работает с JSON, Avro, Parquet, ORC, XML.
- Поддержка SQL – совместим с ANSI SQL и PostgreSQL.
- Multi-Cloud – работает в AWS, Azure и Google Cloud.
- Time Travel – возможность отката данных к прошлым версиям без бэкапов.
- Высокая интеграция – работает с S3, Glue, Kafka, Flink, BI-инструментами (Tableau, Power BI, Looker, Metabase).

🛠 Когда использовать Snowflake?

- Для облачного хранилища данных (DWH), где требуется гибкое управление ресурсами и аналитика больших данных.
- Для анализа больших объемов данных (Big Data), включая semi-structured данные (JSON, Parquet).
- Когда нужна высокая масштабируемость без управления кластерами.
- Для BI и аналитики с интеграцией в Tableau, Power BI, Looker.
- Для машинного обучения (ML) и AI – поддержка Snowpark и Python.
- Для построения ETL и real-time ingestion – интеграция с Flink, Kafka, Glue, Kinesis.

# **ClickHouse: Быстрая аналитическая база данных**

**ClickHouse** – это колоночная база данных, оптимизированная для аналитики больших данных

## **1️⃣ Чем ClickHouse отличается от PostgreSQL/MySQL?**

| Фактор                      | ClickHouse (OLAP)                       | PostgreSQL/MySQL (OLTP)        |
|-----------------------------|-----------------------------------------|--------------------------------|
| **Архитектура**             | Колонночное хранение                    | Построчное хранение            |
| **Оптимизация под запросы** | Массовая аналитика (OLAP)               | Транзакционные операции (OLTP) |
| **JOIN-ы**                  | Медленные                               | Быстрые                        |
| **INSERT/UPDATE**           | Оптимизирован для batch-загрузки        | Быстрые одиночные операции     |
| **Сжатие данных**           | Высокое                                 | Низкое                         |
| **Поддержка индексов**      | Минимальная (работает через сортировку) | Классические B-Tree индексы    |

📌 **Вывод:**

- **ClickHouse** – идеален для больших объёмов аналитических данных.
- **PostgreSQL/MySQL** – лучше подходят для транзакционных операций (**запись, обновления**).

## **2️⃣ Почему ClickHouse такой быстрый?**

- **Колонночное хранение** – ускоряет агрегации, так как данные читаются по колонкам.
- **Сильное сжатие данных** – в 3-5 раз меньше места, чем в реляционных базах.
- **MergeTree-таблицы** – предсортировка ускоряет `ORDER BY`, `GROUP BY`.
- **Отложенные обновления** – ClickHouse использует асинхронные мержи.
- **Автоматическая шардинг и репликация** – легко масштабируется.

## **3️⃣ Когда использовать ClickHouse?**

📌 **Идеально подходит для:**

- **Аналитики логов, метрик, финансовых данных.**
- **Агрегаций на больших объёмах данных (миллиарды строк).**
- **Систем мониторинга (например, Prometheus + ClickHouse).**
- **Хранения временных рядов (Time-Series Data).**

📌 **Когда ClickHouse – не лучший выбор?**
❌ Если нужны **сложные JOIN-ы и транзакции** → PostgreSQL/MySQL лучше.
❌ Если система требует **частых обновлений и удаления данных**.
❌ Если нагрузка **OLTP (много записей, мало аналитики)**.

## 🎯 **Итог**

- **ClickHouse** – мощная аналитическая база данных с **колонночным хранением** и **высокой скоростью работы**.
- Лучше всего подходит для **аналитики, логов, BI**, а не для **OLTP и транзакционных операций**.
- Позволяет **быстро обрабатывать терабайты данных** благодаря **сжатию и оптимизированным запросам**.

💡 **Если у тебя большие аналитические данные – ClickHouse лучший выбор!** 🚀

# Сравнение Snowflake, Redshift, ClickHouse и S3

| Фактор                  | **Snowflake**                                      | **Amazon Redshift**                               | **ClickHouse**                                           | **Amazon S3**                                               |
|-------------------------|----------------------------------------------------|---------------------------------------------------|----------------------------------------------------------|-------------------------------------------------------------|
| **Тип**                 | Облачное DWH (OLAP)                                | Облачное DWH (OLAP)                               | Аналитическая БД (OLAP)                                  | Объектное хранилище (Data Lake)                             |
| **Архитектура**         | Serverless, вычисления + хранение раздельно        | MPP (разделение по узлам)                         | Колонночное хранение, кластерное или standalone          | Объектное хранилище                                         |
| **Хранение данных**     | S3 (Separation of Storage & Compute)               | Локально на узлах кластера (SSD) + Spectrum (S3)  | Локально на сервере или в S3                             | S3                                                          |
| **Форматы данных**      | **Колонночное хранение (Internal Format)**         | **Колонночное хранение (Compression & Encoding)** | **Колонночное хранение (MergeTree, ReplacingMergeTree)** | **Parquet, ORC, CSV, JSON, Avro**                           |
| **Скалируемость**       | Автоматическая                                     | Требует перезапуска узлов                         | Горизонтальное и вертикальное                            | Автоматическая                                              |

| **Стоимость**           | Оплата за compute + storage                        | Оплата за мощность кластера                       | Бесплатно (open-source) + стоимость серверов             | Платишь только за хранение данных                           |
| **Когда использовать?** | Если нужен управляемый, масштабируемый DWH         | Для мощной аналитики внутри AWS                   | Для быстрого OLAP-анализа больших данных                 | Для долговременного хранения данных и Data Lake             |
| **Когда не подходит?**  | Если нужен полный контроль                         | Если нужна serverless-архитектура                 | Если нужен serverless                                    | Если важна низкая задержка при аналитических запросах       |
