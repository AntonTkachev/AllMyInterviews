## Spark

**Spark** — это фреймворк с открытым исходным кодом для распределённой обработки неструктурированных и
слабоструктурированных данных. Благодаря поддержке вычислений в памяти, **Spark** гораздо производительнее **Hadoop**,
который использует дисковый ввод/вывод на каждом шаге обработки.

![Spark Components](/image/apache-spark-components.png)

**Преимущества Spark**:

- Высокая производительность за счёт вычислений в RAM
- Интеграция с различными источниками данных
- Поддержка SQL-запросов и библиотеки для машинного обучения

### Архитектура Spark

- **Driver** — главный процесс, который преобразует программу в задачи и управляет их выполнением.
- **Cluster Manager** — управляет ресурсами в кластере и распределяет задачи среди исполнителей.
- **Slave Processes** — рабочие процессы, которые выполняют задачи.
- **RDD (Resilient Distributed Dataset)** — распределённая коллекция неизменяемых данных, разделённых на несколько
  разделов для параллельной обработки.
- **DAG (Directed Acyclic Graph)** — граф операций, который используется для распределения задач.

#### Внутренняя архитектура Spark

- **Task** — наименьшая единица работы, которая выполняет набор инструкций.
- **Stage** — несколько tasks, которые выполняют одни и те же операции на данных.
- **Job** — состоит из нескольких stages и выполняется, когда Spark сталкивается с операцией, требующей
  перераспределения данных.
- **Application** — включает несколько job. Job создаётся при вызове действия (action).

- **SparkContext** и **SQLContext** (до Spark 2.x)
- **SparkSession** (начиная с Spark 2.x) объединяет все предыдущие точки входа.

### **Shuffle** — это дорогостоящая операция перераспределения данных между исполнителями, которая используется при операциях

### .repartition() and .coalesce()

Изменяют кол-во партиций в RDD или DataFrame.   
**repartition** – на примерно одинаковые, дополнительно делает операцию Shuffle  
**сoalesce** – на разного размера, не использует Shuffle(вместо этого склеивает разделы), поэтому быстрее

### Преобразования (Transformations) и действия (Actions)

**Transformations** — создают новый RDD из существующего, например:

- **map()**, **filter()**, **union()** (узкие преобразования) - Данные остаются в пределах одного partition, не требуют
  shuffle.
- **groupByKey()**, **aggregateByKey()** (широкие преобразования) - Данные перераспределяются между узлами (shuffle).

**Actions** — операции, которые выполняют действия с данными и возвращают результаты:

- **count()**, **collect()**, **reduce()**, **take(n)**.

### .cache() vs .persist()

Методы `.cache()` и `.persist()` помогают ускорить доступ к данным, если они будут использованы несколько раз в процессе
обработки, избегая повторных вычислений и работы с исходными данными. Однако важно правильно выбрать метод и настройку в
зависимости от объема данных и требований к производительности.

- **`cache()`** – это специализированный метод для кэширования, который по умолчанию использует настройку
  `MEMORY_AND_DISK` для DataFrame/DataSet (и `MEMORY_ONLY` для RDD). Данные сохраняются в памяти, и если памяти
  недостаточно, они будут записаны на диск. Это удобный метод, когда вы уверены, что данные не выйдут за пределы памяти
  или что использование диска допустимо.

- **`persist()`** – более гибкий метод, который позволяет выбрать тип хранения данных в зависимости от потребностей. Вы
  можете указать различные уровни хранения данных: на диске, в памяти или даже на памяти вне кучи.

### Зачем использовать кэширование?

- **Повторное использование данных**: Ускоряет доступ к данным, если они используются многократно.
- **Аналог контрольной точки**: Сохранение промежуточных результатов для дальнейших вычислений.
- **Снижение затрат на удаленный доступ**: Чтение данных с локального диска быстрее, чем из удаленного источника.

### Стратегии соединений (Join)

- **Inner Join** — выводит только совпавшие записи.
- **Outer Join** — выводит как совпавшие, так и несоответствующие записи (левая, правая и полная).
- **Semi Join** — выводит записи, присутствующие только в одном из наборов данных.
- **Cross Join** — соединяет каждую запись одного набора с каждой записью другого набора.

### Broadcast Variables

**Broadcast Variables** — переменные, доступные для чтения на всех узлах кластера. Это помогает экономить ресурсы,
избегая повторной отправки одних и тех же данных.

```scala
val broadcastVar = sc.broadcast(Array(1, 2, 3))
broadcastVar.value // возвращает [1, 2, 3]
```

## Checkpoint в Apache Spark

**Checkpointing** — это механизм в Apache Spark, который позволяет сохранять промежуточные данные в распределенное
хранилище (например, HDFS) для обеспечения надежности и восстановления состояния при сбоях.

### Зачем использовать checkpoint?

- **Восстановление после сбоя**: Если задача не может быть завершена из-за сбоя, Spark может восстановить данные из
  последнего checkpoint.
- **Гарантия устойчивости**: За счет сохранения промежуточных состояний, Spark гарантирует, что после сбоя можно
  продолжить вычисления с минимальными потерями данных.

### Как работает checkpoint?

- Checkpointing сохраняет состояние RDD или DataFrame в долговременное хранилище (например, HDFS).
- Этот процесс удаляет информацию о вычислениях, связанных с RDD, что улучшает производительность при обработке больших
  объемов данных.
- Используется, как правило, в долгих и сложных вычислениях, где потеря данных может привести к повторному выполнению
  дорогих операций.

### Когда использовать?

- **При длинных операциях**: Например, при обработке больших объемов данных или выполнении сложных вычислений.
- **Для обработки потоковых данных**: В Spark Streaming checkpointing используется для обеспечения устойчивости к сбоям
  в потоках данных.

### Настройка

Чтобы включить checkpointing в Spark:

``` 
spark.sparkContext.setCheckpointDir("hdfs://path_to_checkpoint_dir")
```

Важные замечания

- Checkpointing может замедлить производительность из-за записи в хранилище.
- Используйте его разумно: не всегда требуется сохранять все промежуточные результаты.
- Для Spark Streaming checkpointing критичен для восстановления состояния при сбоях.

**Спекулятивное выполнение задач (Speculative Execution)**

Спекулятивное выполнение позволяет повторно выполнить медленно выполняющиеся задачи на другом воркере, чтобы ускорить
обработку. Это полезно, когда задачи на отдельных узлах работают слишком медленно.

RDD vs DataFrame vs DataSet

- RDD — это распределённая коллекция данных без схемы, которая является immutable.
- DataFrame — распределённая коллекция данных с именованными столбцами, аналог таблицы в реляционной базе данных.
- DataSet — расширение DataFrame с дополнительной безопасностью типов, доступное только в Scala/Java.

### RDD vs DataFrame vs DataSet

|                        | **RDD**                                      | **DataFrame**                                     | **DataSet**                                                     |
|------------------------|----------------------------------------------|---------------------------------------------------|-----------------------------------------------------------------|
| Представление данных   | Не структурированные данные без схемы        | Структурированные данные с именованными столбцами | Структурированные или полуструктурированные данные с типизацией |
| Оптимизация            | Не поддерживает оптимизацию                  | Использует Catalyst для оптимизации               | Использует Catalyst для оптимизации                             |
| Схема                  | Схему нужно указывать вручную                | Схема определяется автоматически                  | Автоматическое определение схемы или использование SQL Engine   |
| Операции агрегирования | Медленнее по сравнению с DataFrame и DataSet | Поддерживает более быстрые операции агрегирования | Быстрее, чем RDD, но немного медленнее, чем DataFrame           |
