## KAFKA

**Apache Kafka** - это распределенная платформа потоковой передачи событий с открытым исходным кодом, предназначенная
для обработки больших объемов данных в реальном времени.

### Основные компоненты:

- **Admin Client** — полезен для выполнения административных команд из клиентского приложения без использования
  инструментов CLI и GUI.
- **Consumer Group** — партиции в топиках делятся между потребителями в группе.
- **Compacted Topic** — хранит только последнее сообщение по ключу, что эффективно для хранения актуальных данных,
  например, состояния пользователя.

### Оптимизация

**Kafka Compression** — сжатие данных с помощью кодеков, таких как gzip или snappy. Минус: увеличение нагрузки на
процессор при распаковке сжатых данных на стороне потребителя.

**Kafka Producer Batch** — объединение нескольких сообщений в пакет для отправки брокеру.

### Репликация и отказоустойчивость

- **Replication Factor** — определяет количество реплик каждой партиции. Обычно рекомендуется использовать значение 3
  для обеспечения отказоустойчивости.
- **Горячие партиции** (Hot Partitions) могут возникать, если данные не равномерно распределены по ключам, что приводит
  к избыточной нагрузке на одну партицию. Важно использовать стратегию партиционирования, которая минимизирует эту
  проблему.

### Kafka Acks и Delivery Semantics

**Kafka Acks** — параметр, который определяет, сколько подтверждений (acks) должен получить продюсер от брокера, чтобы
считать запись успешной. Важно выбрать подходящее значение для аcks в зависимости от того, что важнее: **скорость** или
**надежность**.

- **acks=0** — Продюсер не ожидает никаких подтверждений от брокера. Сообщение считается доставленным сразу после его
  отправки. Это минимизирует задержки, но не гарантирует, что сообщение действительно будет записано в Kafka.

- **acks=1** — Продюсер получает подтверждение от **лидера** партиции, что сообщение записано в журнал. Это быстрее, чем
  `acks=all`, но не гарантирует, что сообщение будет успешно реплицировано на все серверы кластера. Потенциально
  возможна потеря данных, если лидер партиции выйдет из строя до того, как репликация завершится.

- **acks=all (-1)** — Продюсер получает подтверждение от **всех реплик** партиции, что сообщение было записано на все
  реплики. Это наиболее надежный вариант, так как гарантирует, что данные не будут потеряны, даже если один из брокеров
  выйдет из строя. Однако это увеличивает задержки и снижает пропускную способность.

**Что выбрать?**

- Для **надежности** используйте `acks=all`, что гарантирует, что данные не будут потеряны в случае сбоев.
- Для **скорости** используйте `acks=1`, что ускоряет процесс, но увеличивает риск потери данных.
- **acks=0** используется редко, только когда надежность не важна и приоритетом является минимизация задержек.

**Consumer Delivery Semantics:**

- **At least once** — Гарантируется, что сообщение будет доставлено хотя бы один раз, но могут быть дублирования. Это
  связано с тем, что если продюсер не получил подтверждение вовремя, он может отправить сообщение повторно.
- **At most once** — Сообщение может быть потеряно, но не будет дублироваться. Это может быть полезно для случаев, когда
  потеря сообщения не является критичной.
- **Exactly once** — Гарантируется, что сообщение будет доставлено только один раз. Это требует включения
  идемпотентности (`idempotence=true`) на стороне продюсера, что позволяет избежать дублирования сообщений при ошибках в
  процессе передачи.

### Kafka Connect

Kafka Connect - это компонент для подключения Kafka к внешним системам, таким как базы данных, поисковые индексы и
файловые системы.

- **Source Connectors** — для загрузки данных в Kafka.
- **Sink Connectors** — для выгрузки данных из Kafka.

### Архитектура:

- **Worker** — инстанс/сервер Kafka Connect.
- **Connector** — Java класс с пользовательскими настройками.
- **Task** — процесс, создаваемый коннектором.

### Примечания:

- Масштабирование Kafka требует внимательной настройки количества партиций и брокеров. Очень высокое количество партиций
  может привести к перегрузке сети или брокеров.
- Рекомендуется внимательно отслеживать **синхронизацию реплик** (`in-sync`) и производительность системы для
  минимизации потерь данных.
